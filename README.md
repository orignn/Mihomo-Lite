# Mihomo Lite

**轻量的 Windows 代理启动器：导入配置，点击连接，在托盘中运行。**

Mihomo Lite 将 [mihomo](https://github.com/MetaCubeX/mihomo) 内核、[Zashboard](https://github.com/Zephyruso/zashboard) 面板和本机管理页面组合在一起，提供配置、订阅、规则与日常连接管理。普通使用不需要管理员权限，不需要自行搭建面板。

当前版本：**v0.6.18** · 平台：**Windows x64** · 当前仓库提供：**源码**

[GitHub 仓库](https://github.com/orignn/Mihomo-Lite) · [Releases](https://github.com/orignn/Mihomo-Lite/releases)

> 本项目不提供代理节点或订阅服务。请使用你自己的合法配置，并遵守当地法律及服务提供方的使用条款。

## 功能概览

- **连接与托盘**：连接、断开、重启内核，管理 Windows 系统代理；支持开机自启、静默启动和托盘操作。
- **配置与订阅**：导入或编辑 YAML，管理多份配置，手动或定时更新订阅，查看服务端提供的流量与到期信息。
- **分享链接导入**：支持 SS、VMess、VLESS、Trojan、Hysteria2/hy2、TUIC 的常见分享格式，转换在本机完成，不上传到第三方转换服务。
- **自定义规则**：编辑、排序、批量操作、导入导出和规则模拟；支持固定的「统一代理」出口，减少跨订阅切换时的策略名问题。
- **个性化设置**：用简单表单调整日志和 DNS，也可展开高级 YAML 与只读最终配置预览。全局与单份配置设置独立保存。
- **运行与维护**：自动/固定端口、可选启动连接及有限次数的崩溃重连、连接诊断、日志、完整配置备份与还原。
- **组件检查**：内核与面板使用固定官方发布源，下载须通过 SHA-256 校验；下载、安装与回滚分开操作。

## 下载与开始使用

**仓库提供源码；完整安装包由 GitHub Actions 在推送版本标签或手动运行时构建，成功发布后可从 [Releases](https://github.com/orignn/Mihomo-Lite/releases) 下载。** 若 Releases 尚无安装包资产，请使用下文源码构建说明。不要把 GitHub 的「Source code」压缩包当作安装包。

取得 Windows x64 完整包后：

1. 核对发布说明与 SHA-256，确认下载的是完整安装包。
2. 解压到一个可写的固定目录，不要在压缩包里直接运行，也不要只取出一个 EXE。完整包已经带有内核、面板和公开 Geo 数据资源。
3. 双击包内的启动器。需要重新打开管理页面时，在托盘菜单中选择「启动器页面」。
4. 在「配置管理」中选择「选择 YAML」「粘贴 YAML」或「添加订阅」。导入并校验成功后，点击「连接」。
5. 连接后按需打开 Zashboard，选择节点、查看连接或调整规则模式。点击「断开连接」停止内核并恢复连接前的系统代理。

**退出程序请使用托盘菜单中的「退出」**。关闭查看窗口不等于结束启动器或内核；具体行为取决于窗口设置。

默认启动器页面为 <http://127.0.0.1:17653/>，自动模式遇到端口占用时会避让。实际端口以「本机连接信息与复制」或托盘打开的页面为准。

## 配置与订阅

- 优先使用完整的 Clash/mihomo YAML 订阅。也可以导入常见分享链接；特殊传输、插件或不支持的参数建议直接使用完整 YAML。
- 分享链接批量导入中，任一条目不支持或校验失败会整批拒绝，不静默丢弃节点，也不覆盖原配置。
- 定时订阅更新默认关闭，可按每条订阅选择每 6 小时、12 小时、每天或每周。只有启动器运行期间才会检查到期更新。
- 「订阅下载设置」默认推荐「自动」：已连接时代理优先，符合回退条件的临时失败再试直连；未连接时直连。「当前代理」不会回退直连。UA、条件下载与失败等待位于高级选项。
- 保存下载设置本身不会下载订阅或重连；连接中切换配置或更新当前订阅会自动重连。编辑 YAML 或个性化设置后，需要重新连接以应用。
- 套餐信息来自订阅响应头或可识别的节点提示；节点提示中的流量会标为估算，缺失数据不会被补造。

订阅更新可能覆盖对订阅原始 YAML 的手工修改。希望长期保留的日志、DNS 等调整，优先使用「个性化设置」；分流调整使用「自定义规则」。

## 自定义规则与个性化设置

### 自定义规则

启用的自定义规则按界面顺序放在订阅规则之前，并在切换配置、更新订阅后继续保留。已连接时「保存并应用」会校验并尝试热重载，未连接时在下次连接应用。

跨订阅使用的代理规则推荐选择「统一代理」。旧规则不会自动迁移：如果规则指向新订阅没有的策略组，需要手动调整或停用，再导入/连接。不要为了消除报错随意改为 DIRECT，这会改变分流意图。

规则模拟仅对支持的范围给出结果；「无法确定」不等于实际一定不命中。

### 个性化设置

不确定时保持「沿用订阅」。DNS 表单只调整服务器地址，不自动开启原配置中关闭的 DNS，也不替换其他高级 DNS 字段。高级 YAML 与最终预览默认折叠；保存设置后需重新连接。

**最终配置预览可能包含节点密码或订阅地址，请勿截图公开或直接粘贴到 Issue。** YAML/规则草稿有未保存提醒，但浏览器草稿不是配置备份，关闭或刷新页面前仍应确认保存。

## 运行设置

- 开机自启、静默启动、窗口关闭行为与自动连接是不同设置。启动连接和崩溃重连默认关闭，保存开关不会立即连接。
- 自动端口会避让占用；固定端口不可重复，遇到占用会明确报错，不强杀其他程序。
- **端口设置保存后需从托盘退出并重新启动程序**。「重启」按钮只重连内核，不应用新的启动器端口。
- 代理监听和管理 API 仅限本机；面板密钥由启动器在本机保存。

## 备份与升级

升级前在「维护 → 备份与还原」导出完整备份，并妥善保管原安装目录。

配置备份包含已保存的配置、订阅信息、自定义规则、更新设置、独立覆写与端口偏好等；**备份文件不加密，可能包含节点凭据与订阅令牌**。它不包含内核、面板、浏览器草稿、启动器 API 密钥及全部本机启动设置，不是整个安装目录的镜像。

手动升级建议：

1. 从托盘退出旧版，确认启动器与内核均已退出后再操作，不覆盖运行中的文件。
2. 将新版完整包解压到另一个目录，保留旧目录作为回退；不要将新包中的示例或空白数据直接覆盖旧用户数据。
3. 启动新目录的程序，在未连接时从备份还原配置，再核对端口、开机自启及其他本机设置。还原会替换配置集合与规则。
4. 确认新版正常后再处理旧目录；不要同时运行两个安装目录中的启动器。

开发工作区内的正式入口升级须使用受控发布流程，不通过手工替换单个组件维持发布身份。

## 常见问题

**导入订阅提示策略不存在？**

检查启用的自定义规则是否仍指向旧订阅的策略组。先停用相关规则并保存，再导入新配置；需要跨订阅生效的规则可改为「统一代理」。

**连接失败，或者系统代理没有恢复？**

查看「连接诊断」和「维护 → 日志」，按提示核验内核、端口与代理状态。恢复记录会用于下次启动时核验旧会话；身份、权限或代理归属不确定时，程序会停止自动处理，不擅自覆盖其他软件的代理。异常退出后不是即时常驻恢复，不能当作全局断网保护。

**没有效果的应用怎么办？支持 TUN 吗？**

本项目使用 HTTP/SOCKS5 代理和 Windows 系统代理。忽略系统代理的应用需自行配置。当前不支持 TUN、局域网共享或额外入站监听，生成运行配置时会关闭 TUN 和 LAN 访问。

**首次使用还需要下载 Geo 数据吗？**

按本文发布流程制作的正式完整包应包含两份 DAT 和 MetaDB 数据库；源码仓库不附带这些资源。远程 provider 等其他订阅资源仍可能需要联网，内置数据库不意味着所有配置都能离线使用。

## 从源码构建

适用于开发者。环境要求：Windows、Go 1.23 或更新版本、PowerShell 5.1 或更新版本；默认前端回归另需 Node.js 18 或更新版本。前端为原生 HTML/CSS/JavaScript，不需要 npm 打包。

默认受控构建禁止自动联网下载依赖。首次克隆后，需先明确准备 Go 依赖，并使用与构建脚本一致的本地缓存目录。例如，在源码根目录执行一次联网准备：

~~~powershell
$env:GOCACHE = "$PWD\.cache\toolchain\gobuild"
$env:GOMODCACHE = "$PWD\.cache\toolchain\gomod"
$env:GOPATH = "$PWD\.cache\toolchain\gopath"
$env:GOPROXY = "https://proxy.golang.org,direct"
$env:GOSUMDB = "sum.golang.org"
go mod download
~~~

依赖准备完成后，运行 [统一构建入口](<tools/build-release.ps1>)：

~~~powershell
.\tools\build-release.ps1
# Node 不在 PATH 时可以明确指定：
.\tools\build-release.ps1 -NodePath 'C:\path\to\node.exe'
~~~

默认先执行 Go 与前端回归，再把 EXE、构建清单和测试证据写入缓存，不覆盖日常入口，不启动测试程序修改真实系统代理。依赖外部官方内核的配置/覆写测试在源码克隆缺少资源时会明确 SKIP，不等于这些场景已通过。源码仓库不包含 `runtime/`、`data/` 运行组件或两份 DAT，单独编译出的 EXE 也不是完整安装包。干净源码克隆可执行默认构建；`-Publish` 则是已有正式工作区的本地构建、采用与打包流程，不是 GitHub 上传命令。详细说明见 [开发指南](<docs/DEVELOPMENT.md>)。

## 开发目录与发布边界

~~~text
cmd/          Go 源码、嵌入页面与资源
assets/       源图标
tests/        可复用测试
tools/        构建、检查、打包及维护工具
docs/         公开开发、发布与精简更新记录
build.ps1     底层受控构建入口

# 本地生成或安装后使用，不提交源码仓库：
.cache/       构建、依赖、隔离测试、下载和打包暂存
archive/      历史产物与本地归档
release/      本地当前发布包与清单
runtime/      运行内核
data/         配置、订阅、规则、面板和数据库
logs/         本地日志
launcher.json 本机设置与 API 密钥
CURRENT.json  本地构建/发布身份
~~~

源码提交与二进制发布分开：Git 仓库只提供审查后的源码、测试、源资源及公开说明；完整 ZIP 由 [发布工作流](<.github/workflows/release.yml>) 在托管环境从固定官方资源构建，并作为 Release 资产上传。不压缩上传整个工作区，不发布用户数据、缓存或历史测试环境。

正式发布流程参见 [发布指南](<docs/RELEASE.md>)。维护正式包应使用官方可核验的公开资源白名单，不能从用户运行区或私有测试环境取数据库。新包须同时包含经同批公开上游摘要核验的两份 DAT，并保留 MetaDB；普通构建和打包不自动联网。发布前需要保持正式入口、清单、包内载荷与 SHA-256 一致，并完成严格工作区检查与公开载荷审查。
